## Post-capstone — Mentor review feedback, round 1: live correctness judging (2026-10-27)

Ragini had a review session with an IK mentor after the Day 7 submission prep. His feedback covered seven areas: persistent child-profile DB, login/authentication, child-info access control, prescription/doctor-visit tracking, privacy consents, scope/rate limits ("limits and barriers"), and human-in-the-loop review — plus one item she asked to start on immediately: **LLM-as-judge correctness validation running on the live response itself, not only inside `eval.py`'s offline GEval scoring.**

**Why this one first:** `eval.py`'s GEval metric already does LLM-as-judge correctness scoring — but only offline, against the 20-query golden set, after a response has already been generated. Nothing was checking correctness on an actual live response before a parent saw it. The mentor's point was that the judge needs to sit in the request path itself.

**The design decision:** rather than building a second, parallel judging agent/pipeline, extended the existing Safety Critic (`agents/safety_critic.py`) — which is already an LLM-as-judge mechanism running on every live response — with a fifth check, `is_correct`. Considered a standalone `response_judge.py` first, but rejected it: the Critic already has the exact machinery needed (LLM scores named checks → verdict computed in Python from those booleans, never trusted from the model's own self-report → fail-closed if a check is missing), and `main.py`'s three response-generating branches already call `review()` and already suppress on any `flag` verdict uniformly. Adding a key to an existing dict needed **zero changes to `main.py` or `app.py`** — both already treat `checks` generically (`all(checks.values())` for the verdict; `st.json(critic["checks"])` for the transparency panel) — which is exactly the kind of result that confirms the original check-dict design was sound.

**What `is_correct` actually checks, and how it differs from `in_scope` (important — these are NOT the same check):** `in_scope` catches *fabrication* — a claim with no support anywhere in the grounding context at all. `is_correct` catches a response that got context which DOES exist wrong — e.g. swapping which therapy category goes with which condition, or answering a different question than the parent actually asked. A response can pass `in_scope` (every fact traces to something real) and still fail `is_correct` (it misread or misapplied that real thing). Full rubric wording is in `agents/safety_critic.py`'s `_SYSTEM_PROMPT`.

**Verified live:** ran two real queries end-to-end (`"What is autism?"` → info branch, `"What therapies help with ADHD, and are there specialists in Bangalore?"` → pathway branch). Both now report `is_correct: True` alongside the original four checks, with `verdict=pass`. No regression on either branch.

**`is_correct` recalibrated the same day, directly from Ragini's question ("shouldn't it look at overall meaning, semantic based — why is it validating word to word").** Root cause: the Safety Critic's shared "Be rigorous — when in doubt, fail the check" instruction is correctly calibrated for the four original safety checks (a false negative there is worse than a false positive), but `is_correct` inherited that same posture even though it's a quality/accuracy check, not a safety guardrail — so a cautious model treated any phrasing not literally in the KB as suspect. Rewrote `is_correct`'s rubric in `agents/safety_critic.py` to explicitly separate "changes the meaning/facts" (still flag) from "reasonable paraphrase or synthesis across the context" (fine), with one contrasting example of each, and an explicit carve-out from the "when in doubt, fail" default for this one check specifically. **Verified both directions, not just the one that mattered to the demo:** the exact previously-flagged response (same wording, "as part of a comprehensive care plan" included) now passes; a genuinely fabricated misrepresentation (swapping which specialty diagnoses ADHD vs. which does occupational therapy) still correctly flags, for the right stated reason.

## Tier "limits and barriers / HITL" — minimal human-in-the-loop review queue (2026-10-30)

Ragini chose to skip Tier 2 (child info access control, prescription/doctor-visit tracking — both explicitly deferred, see `ARCHITECTURE.md` §14) and build the minimal HITL item instead: persist every Safety Critic verdict, and a review queue to look at flagged ones.

**What got built:** `critic_reviews` table (`db.py`) — one row per Critic call, pass or flag, linked to the `chat_messages` row it reviewed, same `chat_message_id`-linking pattern as `activity_log`. `review_queue.py` (`log_critic_review`, `get_flagged_reviews`, `mark_reviewed`). Wired into `app.py`'s `_log_turn()` for every workflow that actually calls the Critic (info, pathway, daily_support_activity — not out_of_scope or daily_support_clarify, which never reach it). A new sidebar "🚩 Review queue" section lists unreviewed flags with the Critic's reason, the full checks breakdown, and — critically — the actual suppressed text (added a `flagged_response_text` column once it became clear a review queue showing only "something got flagged" with no way to see WHAT is close to useless).

**The one real design decision, stated plainly rather than silently assumed:** this is a SELF-review queue. Every function in `review_queue.py` is scoped to one `parent_id`, same as everything else in this project — a parent sees what got filtered from their own conversations, not a cross-account quality-review tool. A genuine "a clinician/staff member reviews flagged content across every family" workflow needs a separate reviewer role, which doesn't exist (this app has exactly one role: parent). Building that role was explicitly out of scope for "minimal" — documented as deferred in `ARCHITECTURE.md` §14, not quietly assumed away.

**Verified three ways:** `review_queue.py`'s own smoke test (log a pass + a flag, confirm only the flag surfaces, confirm `mark_reviewed` removes it from the default view but it's still findable with `include_reviewed=True`); a real live chat turn confirmed to write a `pass` row (proving the `_log_turn()` wiring actually fires, not just the standalone function); a seeded flagged row confirmed to render correctly in the sidebar (reason, suppressed text, checks) and correctly disappear from the queue after clicking "Mark reviewed."
